# Security and trust / 安全边界

The endpoint, execution computer, server and credentials are controlled by the user. There is no vendor administrator, hidden support credential, anonymous device takeover or central remote-control account. Same-key devices share an identity group; this is not individual-user role based access control.

- Keys: generated high-entropy secrets; server stores SHA-256 digests/version, desktop stores bridge key through Electron OS-protected safeStorage. Basic-text/unavailable protection is rejected. Browser keeps the typed key only during login and clears it afterward; no key/token in URLs or localStorage. Browser cookie is HttpOnly, Secure on HTTPS and SameSite=Strict. Bearer sessions are held in SDK memory.
- Authorization: every device, Host generation, attachment, socket ticket and resource is bound to identity/session. Host explicitly checks published methods, workspace identity, real file paths/symlinks, task ownership and terminal/watch IDs. Native credential service and unrestricted desktop operations are not public. Configuration responses/events redact secrets; empty remote secret inputs preserve existing values.
- Revoke: logout/client revoke/key removal or version rotation closes existing connections as well as rejecting later HTTP. Tickets are short-lived and single-use. Device incarnation replacement cannot be undone by an old socket callback.
- Transport: HTTPS/WSS outside explicit loopback development, exact Origin/CSRF checks, no permissive credential CORS, no ignored certificates, bounded requests/frames/queues, unauthenticated socket timeout and rate/session/device limits.
- Resources: relay never interprets a client path as a server filesystem path. Host performs reads/writes. Media URLs require an active attachment and session. Active HTML/SVG is downloaded, with nosniff and sandbox. File editing checks SHA-256 before replacement; uncooperative external editor races are not a native filesystem transaction guarantee.
- Privacy: no relay conversation, prompt, repository, memory or terminal-output persistence; authentication metadata in SQLite and finite buffers in memory only. Access to a file/history/terminal transfers that requested content. Model and image requests still go to the providers configured by the user on desktop.

TLS terminates on the self-hosted server. Its operator and delivered Web scripts are trusted. This version has no end-to-end encryption and does not protect against a compromised execution computer, server, browser or leaked key. Task/terminal control can execute shell commands with the desktop user's permissions; workspace path guards are not an OS sandbox for arbitrary agent commands.

Use a dedicated domain, protect the digest file/auth database and OS account, keep TLS valid, and revoke lost clients. Server logs avoid request bodies, tokens, files and terminal content; reverse-proxy logging must follow the same policy. No third-party monitoring service is added by the bridge.
